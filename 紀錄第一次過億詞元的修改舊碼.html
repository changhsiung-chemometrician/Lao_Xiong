02

AQP 是做什麼的

AQP 是我用 MATLAB 寫的近紅外光譜（NIR）自動定量程式。簡單說，它把光譜和實驗室量到的數值配對起來，建立一個預測模型，以後只要量光譜，就能估出成分含量。它有一個圖形介面 AQP_gui，也可以用 Run_AQP 整批執行。主要流程是這幾步：

  1. 載入資料從 Excel 活頁簿讀入光譜和參考值，分成校正集、驗證集、轉移集。
  2. 波長對齊不同儀器量的波長點不一樣，先統一到共同的波長格點上。
  3. 儀器間校正轉移用 MDC、PDS 等方法，讓在一台儀器上建的模型，也能用在另一台儀器量的光譜上。
  4. 光譜前處理對光譜做各種前處理，可以一次跑好幾套組合來比較。
  5. PLS 建模用偏最小平方法建定量模型，以交叉驗證決定模型大小。
  6. 預測、比較、作圖用驗證集算預測誤差；Cmp_Results 比較各組結果，StepbyStep_plots 把每一步畫出來。

另外還有幾個分支功能：

  • 平均光譜：把同一樣品的多次掃描平均後再建模。
  • Scan Thru、UDM、多資料集一起處理。
  • SVR（支持向量迴歸），作為 PLS 之外的另一種建模方法。

每一步做完的資料，都包成同一種標準格式 Atrainpketc_*.mat，交給下一步使用。

03

改之前的毛病

今年八月，我把 Run_AQP.m、Cmp_Results.m、StepbyStep_plots.m、Load_DS.m 等幾個檔案合併成一個大檔，總共 73,824 行、925 個函式。

合併是合併了，但每個原來的檔案都帶著自己的一套小工具進來，所以同一個函式常常重複好幾份。最誇張的 saConc2XY，在檔裡有十份。

另一個毛病是資料的傳法。每一步做完，結果不是直接交給下一步，而是先寫成 .mat 檔存到硬碟的 TMP 資料夾，下一步再去資料夾把它讀回來。跑一次，要寫了又讀的暫存檔有 12 到 25 個。

改之前上一步→寫入硬碟 TMP→從硬碟讀回→下一步
改之後上一步→留在記憶體 AQP_mem→下一步

資料不在程式裡流動，而是繞到硬碟去一趟。

指令裡最要緊的一句，是提到 App Designer 的 app 和 GUIDE 時代的 handles。意思是：資料應該留在程式內部傳，不要寫到硬碟再讀回來。

05

改了哪三件事

Claude 先把七萬多行從頭讀過一遍，然後分三步動手。

第一步：合併重複的函式

它把每個函式的內容拿出來比對，註解和空白不算，函式改過的名字也先還原，一輪一輪比到沒有新的重複為止。

結果是 334 個函式名有不只一份，總共 659 份，合併成 302 份，省掉 26,892 行。只有一組不是完全相同：tmp_folder_rm_mk__fdir_wildcard 其中一份多了八月二十日加上的 onCleanup 保護，留下的是有保護的那一份。

第二步：刪掉永遠不會執行的程式碼

一類是 302 段 if false … end 包起來的範例和草稿，共 7,268 行。另一類是 203 個函式，不管從主程式、開啟函式或 .fig 介面上的任何按鈕出發，都呼叫不到，共 18,510 行。

判斷「用不用得到」時，標準放得很寬：只要還在用的程式碼裡任何地方提到它的名字，連寫在字串裡、透過 feval 或 str2func 間接呼叫的都算，就保留。刪完再檢查一次，剩下的 392 個函式全部都呼叫得到。

第三步：暫存檔改放記憶體

這一步最難。四十多個函式、幾十條分支，都是用「資料夾路徑加檔名」去找資料。如果每一處都改成函式直接傳參數，等於要改遍每一條分支，包括測試資料根本跑不到的那些，風險太大。

所以換個做法：程式的寫法不動，只改資料實際放的地方。新增一個只在單次執行期間存在的記憶體倉庫 AQP_mem，作用類似 GUIDE 的 handles。各步驟照舊用原來的路徑存檔、列目錄、讀檔，但凡是 TMP 底下的東西都留在記憶體裡，不寫到硬碟；要給人看的最後結果，照舊寫到硬碟。

總共接上了 57 處讀檔、26 處存檔，以及大約 60 處複製、搬移、刪除。

跑一次產生的 TMP 暫存檔，從 12 到 25 個變成 0 個。

06

怎麼證明沒改壞

Claude 工作的雲端環境沒有 MATLAB，所以改用免費的 GNU Octave 8.4.0 來跑。Octave 和 Windows 上的 MATLAB 有些地方不一樣，例如 Windows 路徑、檔名裡的方括號和大括號、string 型別、各種對話框，所以它另外寫了一批替代函式補上這些差異。新舊兩個版本用的是同一批替代函式，比較才公平。

測試資料是甘蔗：FOSS 儀器的校正集，MicroNIR 儀器的驗證集和轉移集，要預測的是糖度 Brix。一共跑七個場景，涵蓋以下幾類：

  • MDC 校正轉移
  • PDS99[w5] 校正轉移
  • 不做校正轉移
  • 四套前處理一起跑
  • 平均光譜
  • 從載入、執行兩次、比較結果到逐步作圖的完整流程

新舊兩版產生的每一個輸出檔，都用 isequaln 逐欄逐值比對，不允許任何誤差。

七個場景，新舊結果完全相同。

其中第六個場景，新舊兩版都在同一行出錯：PLS_Tcv_P_Avg_All 呼叫 RMS_error_woNaN_N 時，兩個向量長度不一樣。這是原本程式就有的老毛病，不是這次改出來的。這次的原則是先保持原樣，所以沒有去修，只記錄下來留待以後處理。

另外還開了一個「鏡像模式」，讓新版在途中照樣把每個 Atrainpketc 暫存檔寫到硬碟，再和舊版一個一個比對。17 個中間檔，內容完全一樣。這表示不只最後結果相同，連中間每一步都相同。

行數73,824 → 24,374
函式數925 → 392
檔案大小3.08 → 0.95 MB
每次執行的 TMP 暫存檔12–25 → 0
每次執行時間（Octave）30–41 → 20–31 秒
驗證結果7 / 7 完全相同

介面檔 .fig 完全沒動，裡面登記的 14 個按鈕回呼函式都還在。

詞元用在哪裡

一億一千八百多萬個詞元，分成四段。光是修改程式加驗證，就用了九千五百萬；後面寫紀錄、收進目錄、報帳，又用了兩千三百多萬。

修改＋驗證95,023,918 · 113 分鐘
寫成紀錄5,146,248 · 5.6 分鐘
收進目錄14,369,710 · 4.8 分鐘
報帳3,716,273 · 2.2 分鐘

按種類分，絕大部分是「重讀快取」：Claude 每做一步，都要把前面所有的對話和檔案內容重新讀一遍，這部分有快取，價錢很便宜。真正由 Claude 寫出來的內容只有 24 萬個詞元，不到總數的千分之二。

用 Pro 訂閱花了多少錢

先算如果這一場是照 API 牌價付費，要花多少。這場用的是 Claude Opus 5.5，目前的牌價是：一般輸入每百萬詞元 4 美元，輸出 20 美元，重讀快取 0.20 美元，寫入一小時快取 8 美元（用量報告上寫入快取的折算倍數是 2 倍，對應的就是一小時快取）。

種類詞元數單價（美元／百萬）金額（美元）
重讀快取（cache read）116,126,3360.2023.23
寫入快取（cache write）1,890,1538.0015.12
輸出（output）239,09420.004.78
一般輸入（input）5664.000.00

若寫入快取算五分鐘快取（每百萬 5 美元），合計約 37.46 美元。若照上一代 Opus 5 的價錢（輸入 5、輸出 25、重讀快取 0.50 美元），合計約 82.94 美元，也就是前篇「折算實耗 16,588,976」乘上每百萬 5 美元。

但我不是用 API，是用每月 20 美元的 Pro 訂閱（年繳的話是每月 17 美元）。Pro 是固定月費，在用量額度之內，用多用少都是同一個價錢。所以：

這一場實際多付的錢US$0
把月費按天攤（20 ÷ 31 天）≈ US$0.65 / 天
同樣用量照 API 牌價≈ US$43
相當於幾個月的 Pro 月費≈ 2.2 個月

換句話說，這一場在 Pro 底下用掉的是「額度」，不是額外的錢。如果硬要給它一個價錢，按天攤是六毛五美金；按 API 牌價算，是四十三美金左右，等於兩個多月的月費一次用掉。前提是當天沒有超出額度、也沒有開啟另外計費的加購用量。

再換一種算法：指令七十來個字，平均每個字換來一百五十萬以上個詞元，或者大約六毛錢美金的 API 價值。
