伍 · 診斷

最貴的那個習慣

一個算式 一份 60 KB 的 HTML ≈ 1.5 萬 token。寫在第 5 輪，對話走到第 20 輪，它被重送 15 次 ＝ 22.5 萬 token。

同一份檔案改了三次，就是三份都躺在歷史裡，一起被重送。

如果只能挑一件事改，是這一件：不要為了改一行而重發整份檔案。

本週有非常多這樣的回合——「背景色跟首頁不一樣」、「把 readout 那塊拿掉」、「最後兩節刪掉換成帶得走的三句話」、「新標籤貼錯了」。每一次的實質修改都在十行以內，但交付方式是一份完整的、一千多行的 HTML。而且舊的那份不會消失，它留在對話歷史裡，往後每一輪都陪著新的一起被重送。

改一行，重發一千行，
然後兩份一起被讀二十遍。

第二件事是大型 .m 檔的處理方式。今天這場的做法其實已經是對的：檔案上傳進容器後，我用 grep／sed／Python 在容器裡處理，只把需要看的幾百行拉進脈絡，改動也是用腳本打補丁，最後才輸出成品。1.63 MB 的檔案沒有整份進脈絡——如果整份讀進來，光那一次就是四十幾萬 token。這個做法值得固定下來：上傳大檔時，明講「用容器處理，不要整份讀進來」。

第三件事最實際：那條 MATLAB 線走錯了介面。AQP_gui 這四場——相依閉包分析、函式邊界掃描、批次補丁、回歸驗證——正是 Claude Code 的主場。而您的截圖明白寫著，Claude Code 的週上限在 8/31 前多 50%，那是跟一般對話分開的桶子。把最重的那條線挪過去，等於把本週三成五到四成五的量從一個快滿的桶子倒進一個更大的桶子。

還有一個結構性的：index.html 一週重建七次

七次裡有六次是同一個流程：抓 repo、對差集、找出那一個沒進索引的檔、補條目、同步五處計數、驗證。這是標準的機械勞動，而且您在 8/17 那場就已經被提過一次可以用 GitHub Action 自動重建索引。七次併成一次批次處理，或乾脆讓 Action 去跑，這一整類就從帳單上消失了。

陸 · 結論

帶得走的六句話

  1. 用量不是聊出來的，是產出來的。

    閒聊佔不到 3%。七到八成五來自「整份檔案」為單位的交付：MATLAB 重構、外刊體長文、index 維運。

  2. 改一行就說「只給我 patch」。

    本週最貴的單一習慣。小修用 diff 或「告訴我改哪幾行」，不要重發整份；舊版本會一直留在對話裡陪跑。

  3. 大檔上傳時，明講「在容器裡處理」。

    1.63 MB 的 .m 檔整份讀進脈絡是四十幾萬 token；用 grep／Python 只拉需要的幾百行，是幾千。今天這場就是後者。

  4. MATLAB 那條線搬去 Claude Code。

    那是分開的額度，而且 8/31 前還多 50%。本週最重的三成五到四成五，本來就該走那裡。

  5. 一個任務一場對話，做完就開新的。

    Session 91% 而 Weekly 才 77%，說明壓力集中在少數超長對話。長對話的成本是平方級的，不是線性的。

  6. index.html 該讓機器自己跑。

    一週七次同樣的差集比對。批次處理，或接上 GitHub Action——這一整類可以從帳單上整條刪掉。
